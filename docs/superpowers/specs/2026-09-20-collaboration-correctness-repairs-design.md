# 协作正确性与残留问题修复设计

**日期**：2026-09-20  
**状态**：已确认，待实施  
**范围**：协作基线、陈旧版本合并、离线草稿、段落解析、Mermaid 全屏生命周期、E2E 可靠性和质量门禁

## 1. 背景

现有版本号驱动协作流程存在一个核心一致性问题：客户端可能只推进
`baseVersion`，或者把包含未保存本地编辑的编辑器内容写入 `baseContent`。此后保存请求不再能准确表达“用户相对哪个服务器版本做了什么修改”，可能静默跳过本地修改，或用整份客户端内容覆盖远端修改。

另外，服务重启后只恢复版本号而不恢复增量变更，离线保存会错误地清除 dirty 状态，前后端对 frontmatter 的分段规则不同，部分 E2E 因测试数据创建失败而动态跳过，Mermaid 原生全屏的目标和退出清理也不符合已有设计。

## 2. 设计目标

1. `baseVersion` 和 `baseContent` 始终组成同一个已确认服务器快照。
2. 本地有未保存编辑时，不让远端事件修改编辑器内容或客户端基线。
3. 服务重启、增量历史缺失或客户端长时间离线后，仍能安全合并本地和远端内容。
4. 离线草稿仅在服务器确认写入后清除，并在恢复网络后自动同步。
5. 前后端使用一致的 Markdown 段落坐标。
6. Mermaid 原生全屏只展示当前图表和控件，并完整清理浏览器及应用状态。
7. 必测 E2E 不因夹具初始化失败而显示为跳过。
8. Python、JavaScript、格式和完整 E2E 门禁全部通过。

## 3. 核心不变量

### 3.1 原子基线

`state.baseVersion` 精确描述 `state.baseContent`。两者只能在以下时机一起更新：

- 初次加载或显式刷新文件成功；
- 客户端干净时成功应用远端更新；
- 保存请求成功并收到服务器规范内容。

禁止单独推进版本号，也禁止把包含未确认本地修改的编辑器内容写入基线或 `_originalContent`。

### 3.2 dirty 状态的远端更新

本地 dirty 时收到 `remote_edit`、版本缺口或 `external_reload`：

- 不修改编辑器；
- 不修改 `baseVersion`、`baseContent` 或 `_originalContent`；
- 记录存在待合并远端更新，并向用户显示非阻塞提示；
- 下一次保存统一交给服务器合并。

客户端干净时，远端变更仍实时应用，并原子更新编辑器和基线。

### 3.3 确认后才清理

网络错误、离线保存、合并拒绝和解析失败都不能清除 dirty 状态或本地草稿。只有服务器返回成功写入和规范内容后，才允许清除相应草稿。

## 4. 保存与合并协议

### 4.1 请求

服务器挂载的保存请求携带：

- `baseVersion`：客户端已确认版本；
- `baseContent`：该版本的完整内容；
- `content`：本次提交时的编辑器快照；
- `changes`：由 `baseContent` 到 `content` 的段落 diff；
- 现有作者和客户端元数据。

服务端始终根据 `baseContent` 和 `content` 重新计算规范 diff；提交的 `changes`
只用于一致性校验。两者不一致时不写盘，不能仅凭完整客户端内容在版本号碰巧一致时盲目覆盖文件。

### 4.2 版本一致

当 `baseVersion` 等于服务器当前版本时，服务端把规范 diff 应用于当前内容，写盘、增加版本、记录历史并返回完整规范内容。

### 4.3 版本落后

当客户端版本落后时，服务端执行段落级三方合并：

1. 以 `baseContent` 为共同祖先；
2. 计算祖先到客户端内容的本地变更；
3. 计算祖先到服务器当前内容的远端变更；
4. 把本地变更转换到服务器当前段落坐标；
5. 应用转换后的变更，写盘并返回合并后的完整内容。

这条路径不依赖进程内 `changes_by_version` 是否完整，因此服务重启和历史裁剪不会被误判为“没有远端变化”。同段冲突继续遵循项目现有的后写覆盖规则；不同段落变更应同时保留。

### 4.4 无法安全处理

客户端版本超前、缺少必要基线、请求内部不一致或变更无法验证时，服务端不写盘，并通过现有 JSON 成功响应通道返回
`{applied: false, resyncRequired: true, newVersion, content}`。客户端保留本地编辑和草稿，使用返回的服务器快照重建基线后再尝试合并，不能退化为整文件覆盖。

### 4.5 保存期间继续输入

客户端在发请求前保存提交内容快照。响应到达时：

- 编辑器仍等于提交快照：显示服务器规范内容并标记 clean；
- 用户又输入了内容：把“提交快照到当前编辑器”的新增变更转换并应用到服务器规范内容，保持 dirty，并安排下一次保存。

用于重放的前端变换逻辑必须与服务端段落坐标规则使用相同测试样例，避免语言实现漂移。

## 5. 离线草稿

离线保存把当前内容和对应基线写入本地草稿，但保持 `state.dirty = true`。恢复网络后，当前文件自动进入正常保存流程，因此仍享有版本校验和三方合并保护。

草稿只有在服务器确认成功后删除。网络失败、只收到远端通知或 `resyncRequired` 都保留草稿。非当前文件的既有行为仍只提示存在草稿，本次修复不新增后台批量上传机制。

## 6. 段落解析契约

前端 `splitParagraphsWithDelims` 与后端 `split_paragraphs_with_delims` 必须对以下输入产生相同的段落数组和索引：

- frontmatter 由 `---` 或 `...` 关闭；
- frontmatter 后有一个、多个或没有空行；
- 文件只有 frontmatter；
- frontmatter 后紧接正文；
- fenced code block 和数学块中包含空行或分隔符。

实现以现有后端规则为规范来源，前端调整到相同行为，并增加共享边界样例验证。

## 7. Mermaid 原生全屏

原生 Fullscreen API 的目标是当前 `.mme-overlay-item`，不是 `document.documentElement`。由于源图表位于 Vditor 内容树而不是 overlay 子树，原生全屏时在当前 overlay 内创建临时视觉副本，使图表和工具栏都属于全屏元素，同时不移动或污染 Vditor 源 DOM。

全屏控件只操作当前视觉实例。退出后销毁临时副本，恢复进入全屏前的缩放、平移和主题状态。若文件切换、重新渲染或 Undo/Redo 使源图表消失，先调用 `document.exitFullscreen()`，再清理 overlay 和内部状态。原生 API 失败时继续使用现有应用内回退模式。

## 8. E2E 可靠性

需要访问私有测试挂载的 API 请求显式携带 `X-Admin: 1`，不依赖浏览器请求是否自动产生 `/admin` Referer。

测试数据创建、挂载发现或必要控件不存在时，必测流程直接失败并显示实际原因。运行时 `test.skip()` 只允许用于明确、预先声明的平台能力差异，不能用于掩盖夹具失败。

## 9. 组件边界

- `nas_md/webserver/file_version_store.py`：版本校验、规范 diff 和服务端三方合并。
- `web/sync_layer.js`：干净状态应用远端事件，dirty 状态排队通知。
- `web/app.js`：保存快照、基线提交、响应协调、输入重放和离线草稿。
- `nas_md/webserver/paragraph_diff.py` 与前端 diff 工具：统一段落契约和转换语义。
- `web/mermaid_enhancer.js`：原生/回退全屏生命周期及临时视觉实例。
- Playwright 夹具和相关规格：可靠创建测试数据，禁止假绿。

不引入文件锁，不改变协作产品规则，不重构无关模块，也不进行全仓库格式化重写。

## 10. 测试策略

所有生产修复遵循 RED-GREEN：先新增能够复现问题的失败测试，确认失败原因正确，再实施最小修复。

### 10.1 Python

- 服务重启后陈旧客户端不会覆盖远端段落；
- 增量历史缺失或被裁剪时仍走安全三方合并；
- 版本超前和无效基线返回 `resyncRequired` 且不写盘；
- 同段后写覆盖和不同段合并规则保持不变；
- frontmatter 和 Markdown 块级边界样例。

### 10.2 前端与 E2E

- dirty 状态收到远端更新不改变编辑器或基线；
- 保存后同时保留本地和远端不同段落修改；
- 保存期间继续输入不会丢失且仍保持 dirty；
- 离线保存保持 dirty，恢复网络后自动提交并清除草稿；
- 前后端段落索引边界样例一致；
- 原生全屏调用当前 overlay item，图表和控件可见；
- 源图表消失时退出浏览器全屏；
- 管理员夹具失败时测试失败而不是跳过。
